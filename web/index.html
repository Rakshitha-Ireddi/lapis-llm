      How it works

      Three steps per machine. Then forget which machine is which.

      1. 1

        Run the agent

        Install the package and point the agent at your master. It detects the GPU or unified memory and prints a fingerprint.

        $ pip install lapis-llm
$ lapis agent --master http://lapis.local:8080
      2. 2

        Approve the fingerprint

        The machine shows up as pending on the Nodes page. Compare fingerprints, approve, and it receives its node secret.

        fingerprint
4B:55:2F:49:BA:50:40:20
F7:C3:57:C4:AE:95:F4:50
      3. 3

        Place a model

        Add a model by size and runtime. Admission checks memory on every node; placement picks the tightest fit and explains every refusal.

        ✓ gaming-pc  needs 5.79, 6.40 free
✗ macbook    runtime not offered
✓ spark      121.00 free

      One endpoint

      If it speaks OpenAI, it already works.

      Chat completions, completions and embeddings, streaming included. Clients choose a model by name; the router finds the machine. GET /v1/models lists everything running across the fleet.

      • Scoped API keys, hashed at rest, shown once
      • X-Lapis-Node header tells you who answered
      • Prometheus metrics on /metrics
      from openai import OpenAI

client = OpenAI(
    base_url="http://lapis.local:8080/v1",
    api_key="lap_...",
)
stream = client.chat.completions.create(
    model="qwen2.5-coder-14b",  # served by studio-pc
    messages=[{"role": "user", "content": "Write a haiku about GPUs"}],
    stream=True,
)
for chunk in stream:
    print(chunk.choices[0].delta.content or "", end="")

      Features

      Small enough to understand. Complete enough to trust.

      • Memory admission

        Every start is checked against free memory minus a reserve, per GPU on discrete cards. Refusals come with the numbers.

      • Best-fit placement

        Small models pack onto small machines so the big box stays free for the 70B. Pin a model to a node whenever you like.

      • Fingerprint enrolment

        New machines wait for approval. Only the agent holding its identity can claim the node secret, so a leaked ID gets nobody in.

      • Self-healing

        After an agent or master restart, models that should be running come back one at a time. Models you stopped stay stopped.

      • Scoped API keys

        Separate keys per person or app, with inference and metrics scopes. Revoke one without touching the rest.

      • Drain & move

        Taking a machine offline? Drain it, move its models elsewhere, and clients never notice the address changed.

      • Backup & restore

        Export models, nodes and keys as JSON. Restores preview exactly what will be added, kept and removed.

      • Audit & metrics

        Every admin action is logged with who, what and when. Prometheus metrics for requests, tokens and node headroom.

      FAQ

      Questions people ask first

      Is this a Kubernetes replacement?

      No. LapisLLM is deliberately small: a control plane for a handful of machines you own. No scheduler, no cluster networking, no hosted service.

      Do I need a GPU to try it?

      No. lapis demo starts a master and five simulated nodes on one laptop, and this website runs the same simulation in your browser.

      Which runtimes are supported?

      llama.cpp (llama-server) on Windows, Linux and macOS, vLLM on Linux, and MLX (mlx_lm.server) on Apple Silicon. The agent launches them as child processes and proxies requests.

      Can a model span two GPUs?

      Not yet. Admission checks each card on its own, so a 10 GiB model will not be placed on two 8 GiB cards. Tensor-parallel placement is on the roadmap.

      Is it safe to expose to the internet?

      Run it on a trusted LAN or behind a TLS reverse proxy. Admin sessions are signed, keys are hashed, and agents only accept calls carrying their node secret. mTLS between master and agents is planned.

      Try it on your laptop first.

      A master, five simulated machines and live traffic. No GPU required.
